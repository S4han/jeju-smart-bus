## 3. PRIV-001 — 서버 DB 영구 저장 금지

설계 근거:
- 서버 측 저장소 미도입: DB·KV·Blob·Edge Config 등 사용하지 않음(AGENTS.md 규칙 4·5, GATE-06 Marketplace 과금 위험과도 일치).
- 서버 함수 입력은 정류장 ID 등 비위치 파라미터로 한정. `lat`, `lng`, `x`, `y`, `latitude`, `longitude`, `coords` 등 좌표성 필드가 오면 **400으로 거부**하고 값은 로그에 남기지 않음(TASK-004 단위 테스트).
- 경로 탐색은 브라우저에서 수행(D-01) → 서버가 좌표를 받을 이유가 없음.

예외 경로: 도보 API 키를 서버에 둬야 해서 좌표가 서버를 경유하게 되면(R-18) 이 판정은 **재검증 대상**이다. 그 경우에도 저장 없이 요청 처리 후 폐기, §4 로그 규칙 적용.

## 4. PRIV-002 — 로그 최소화

| 로그 종류 | 위험 | 규칙(구현 체크리스트) |
|---|---|---|
| Vercel 접근·런타임 로그 | 요청 경로·쿼리스트링이 기록됨(`requestPath` 단위 조회 가능) | 좌표를 URL 경로·쿼리에 절대 넣지 않음. 서버로 보낼 경우 요청 본문 사용 |
| 서버 함수 `console.*` | 런타임 로그에 남음 | 요청 본문·헤더·외부 응답 원문 출력 금지. 오류는 정규화된 코드(`unavailable` 등)와 요청 ID만 |
| 외부 API 오류 메시지 | 키·URL 포함 가능 | 키 마스킹 후 코드만 기록 |
| 브라우저 콘솔 | 사용자 기기에만 남지만 디버깅 습관으로 좌표 출력 위험 | 좌표 `console.*` 출력 금지(리뷰 체크). 개발용 로그도 커밋 금지 |
| 오류 수집 도구(Sentry 등) | 상태·URL·breadcrumb에 좌표 포함 | MVP 미도입(D-13 취지). 도입 시 PRIV 재검증 |
| 분석 도구 | 페이지 URL·이벤트 | Vercel Web Analytics·Speed Insights·로그 드레인 미사용(D-13 승인) |
| 빌드 로그 | 해당 없음 | — |
| 저장소·테스트 픽스처 | 실제 사용자 좌표 커밋 | 픽스처 좌표는 정류장 공개 좌표 또는 합성 좌표만 |

조건부 사유:
1. **D-22(신규):** 도착정보 요청 `GET /api/arrivals?stopId=…`는 정류장 ID가 접근 로그에 IP와 함께 남는다. 정류장 ID는 좌표가 아니고 공개 시설 식별자이지만, 사용자 관심 위치를 간접적으로 드러낼 수 있다.
   - (A) GET + URL의 정류장 ID 허용 → CDN 캐시로 호출량 절감(NFR-002에 유리). 로그 보존은 Vercel 기본값에 한정, 드레인 없음.
   - (B) POST + 본문 → URL 로그에 남지 않으나 CDN 캐시 불가 → 버스 API 호출량 증가.
   - **결정: (A) 승인(2026-10-26).** 정류장 ID는 PRD가 정의한 "위치정보(현재·선택 위치)"가 아니며, 쿼터 보호 효과가 큼. 조건: 로그 드레인 없음(D-13), 서버 측에서 정류장 ID와 IP를 결합해 저장하지 않음.
2. ~~Vercel 로그 보존 기간 미확인~~ → 원문 확인: "Runtime logs are stored for 1 hour on Hobby, 1 day on Pro, and for 3 days on Enterprise". 빌드 로그는 무기한 보존이지만 사용자 데이터가 들어가지 않음. 런타임 로그는 Request Path를 기록하며 쿼리스트링 포함 여부는 명시가 없어 포함될 수 있다고 보고 규칙 유지.

## 5. PRIV-003 — 캐시

| 캐시 | 규칙 |
|---|---|
| Vercel CDN(공유 캐시) | 도착정보 응답(정류장 ID 키)만 짧은 `s-maxage`. 좌표가 포함될 수 있는 응답은 `Cache-Control: no-store` |

| 브라우저 HTTP 캐시 | 좌표가 URL에 없으므로 좌표 관련 캐시 항목 없음 |
| Web Storage·IndexedDB·쿠키 | 좌표 저장 금지. 1km 확대 동의 여부 등 상태도 MVP에서는 저장하지 않음(세션 메모리) |

| URL·history·공유 링크 | 좌표·검색 위치를 URL에 넣지 않음 → 뒤로 가기 기록·공유 링크로 노출되지 않음 |

## 6. PRIV-004 — 외부 서비스로 전달되는 좌표

### 6.1 NAVER Dynamic Map — 조건부

- 전달: 지도 중심을 사용자 위치로 이동하면 타일·SDK 요청이 그 주변 영역을 드러냄. 사용자 위치 마커는 브라우저에서 그려지며 정확한 좌표가 별도로 전송되는지는 **미확인**(SDK 내부 동작 — TASK-010에서 네트워크 요청 관찰로 확인).
- 제공업체 저장·재이용 조건: NAVER Cloud 이용약관·개인정보처리방침 원문 미열람(네트워크 차단).
- **조사 현황(2026-10-26, 2차):**
  - [NCP 약관 목록](https://www.ncloud.com/policy/terms/maps)에서 "Maps 서비스 이용약관"(파일 `[민간]Maps서비스이용약관_v0.4`)과 "위치기반서비스 이용약관"이 별도로 존재함을 원문 확인
  - 약관 본문(PDF, `xv-ncloud.pstatic.net`)은 **네트워크 정책 차단**으로 미열람. NCP 가이드(`guide.ncloud-docs.com`)는 사이트 보안 필터로 자동 접근 거부
  - **검색 요약(근거 B, 원문 미확인):** Maps 약관에 "서비스 이용정보가 네이버㈜에 제공되고 보관·활용될 수 있으며 그에 대해 (고객이) 이용자 동의를 받아야 한다"는 취지의 조항, 계약 종료 후 데이터 삭제 조항이 있다고 요약됨. 사실이면 **우리 서비스가 지도 이용 전 이용자 고지·동의를 받아야 함**(NAVER 검색 API 약관 11.5·11.6과 같은 구조)
  - 좌표·뷰포트 요청 로그의 보관 기간·익명화 여부는 확인되지 않음
- 판정: 기존 PoC(제주시 고정 중심)는 사용자 위치를 쓰지 않으므로 영향 없음. **사용자 위치로 지도 중심을 옮기는 기능(TASK-011·013)은 아래 확인 전 보류.**
  - [ ] NAVER Cloud Maps 약관·처리방침의 요청 데이터 처리 조항 확인(사용자 또는 차단 해제 후 재조사)
  - [ ] TASK-010에서 SDK 네트워크 요청에 정확한 좌표가 포함되는지 관찰

### 6.2 장소 검색(U-001) — 해당 없음(MVP)

**2026-10-26 D-05 확정:** MVP는 외부 장소 검색 API를 쓰지 않는다. 정류장명 검색은 브라우저의 정적 스냅샷에서 수행(네트워크 전송 없음), 지도 직접 지정은 §6.1(NAVER 지도) 조건을 따른다. 아래는 외부 검색 도입 시 기준으로 남겨 둔다.

- 공급자 미정(TASK-008). 원칙: **검색어만 전송, 위치 편향 좌표 미전송**을 기본으로 한다. 좌표 전송이 필요하면 해당 공급자 약관 확인 후 사용자 승인.
- Kakao(후보): 운영정책상 캐시는 사용자 환경 개선 목적만, 데이터 복사·제공 금지. 전달 좌표의 저장·재이용 조항은 미확인.

### 6.3 도보 데이터(U-002) — 보류

- 도보 경로 API를 쓰면 출발·도착 좌표가 반드시 외부로 전달된다. REST 키를 서버에 두면 자체 서버도 경유(R-18).
- D-06에서 "도보 API 사용"이 선택될 경우에만 해당 공급자 조건을 검증한다. "직선거리 기반 추정" 또는 "미제공"을 선택하면 외부 전달이 없다.

### 8.1 관련 조문 요지 (원문 인용)

| 조문 | 원문 요지 |
|---|---|
| 제2조 1호 | "위치정보"란 "이동성이 있는 물건 또는 개인이 특정한 시간에 존재하거나 존재하였던 장소에 관한 정보로서 「전기통신사업법」…에 따른 전기통신설비 및 전기통신회선설비를 이용하여 측위(測位)된 것" |
| 제2조 2호 | "개인위치정보"란 "특정 개인의 위치정보(위치정보만으로는 특정 개인의 위치를 알 수 없는 경우에도 다른 정보와 용이하게 결합하여 특정 개인의 위치를 알 수 있는 것을 포함한다)" |
| 제2조 4·5호 | 위치정보 수집사실 확인자료 = 수집요청인·수집일시·수집방법에 관한 자료, 이용·제공사실 확인자료 = 제공받는 자·취득경로·이용·제공일시·방법에 관한 자료 — 둘 다 **"(위치정보는 제외한다)"** |
| 제2조 7호 | "위치기반서비스사업"이란 위치정보를 이용한 서비스를 제공하는 것을 사업으로 영위하는 것 |
| 제9조 ① | 위치기반서비스사업(**개인위치정보를 대상으로 하지 아니하는 위치기반서비스사업은 제외**)을 하려는 자는 방송미디어통신위원회에 신고 |
| 제9조의2 ① | 소상공인·1인 창조기업은 신고 없이 시작할 수 있으나, **사업 개시 1개월이 지난 후에도 계속하려면 개시일부터 1개월 이내에 신고** |
| 제16조 ② | 위치정보사업자등은 **위치정보 수집·이용·제공사실 확인자료를 위치정보시스템에 자동으로 기록되고 보존되도록** 하여야 함 |
| 제19조 ① | 위치기반서비스사업자가 개인위치정보를 이용해 서비스를 제공하려면 **이용약관에 명시**(상호·연락처, 권리·행사방법, 서비스 내용, 확인자료 보유근거·기간, 개인위치정보 보유목적·기간 등) **후 동의** |
| 제23조 ① | 목적 달성 시 확인자료 외의 개인위치정보는 **즉시 파기** |
| 제24조 | 동의 철회, 수집·이용·제공의 **일시 중지 요구**(거절 불가, 기술적 수단 필요), 확인자료 열람·고지 요구 |
| 제25조 ① | **14세 미만** 아동의 개인위치정보는 법정대리인 동의 필요 |
| 개인위치정보 처리방침 공개 조항 | 처리방침에 처리목적·보유기간, 확인자료 보유근거·기간, 파기 절차, 제3자 제공 등을 포함 |
| 위반 시 | 확인자료 기록·보존조치 미이행, 동의 없는 수집 등은 과징금(매출액 100분의 3 이하) 대상 조항 존재 |

참고: [네이버 개인정보처리방침](https://policy.naver.com/policy/privacy.html) 10장 — 네이버는 "대부분의 위치기반서비스에서 개인위치정보를 일회성 또는 임시로 이용 후 지체없이 파기"하고, 제16조 제2항에 따라 확인자료를 "6개월 이상 보관"한다고 공개(네이버 자체 서비스 기준이며 Maps API 요청 처리 조건은 아님).

### 8.2 검토 질문

| # | 검토 질문 | 조문 근거로 본 쟁점(판단 아님) |
|---|---|---|
| L-1 | 이 서비스가 **개인위치정보를 대상으로 하는** 위치기반서비스사업인가? 회원가입이 없고 좌표가 브라우저에서만 처리되는 경우는? | 제2조 2호(다른 정보와 결합해 특정 개인 위치를 알 수 있는 경우 포함), 제9조 ① 괄호(개인위치정보 비대상이면 신고 제외) |
| L-2 | 해당한다면 신고 주체·시점 — 소상공인·1인 창조기업이면 개시 후 1개월 내 신고 | 제9조, 제9조의2 |
| L-3 | 이용약관 명시·동의 방식, 개인위치정보 처리방침 공개 | 제19조 ①, 처리방침 공개 조항 |
| L-4 | **확인자료 기록·보존 의무와 PRD 정책의 관계** | 확인자료는 정의상 **위치정보를 제외**하므로 PRD의 "위치정보 서버 DB 영구 저장 금지"와 직접 충돌하지는 않는다. 다만 L-1이 "해당"이면 제16조 ②에 따라 **처리 사실(일시·방법 등)을 서버에 자동 기록·보존하는 장치가 필요**해진다. 현재 설계(D-01·D-11: 서버 저장소 없음)에는 그런 장치가 없으므로 **설계 변경(무료 저장소 도입 — NFR-001 검증 필요)** 또는 범위 재검토가 필요할 수 있다 |
| L-5 | 지도·장소 검색 공급자에 좌표·검색어를 보내는 것이 개인위치정보의 제3자 제공인가 | 제19조 ②·③(제3자 제공 시 고지·동의·통보) |
| L-6 | 14세 미만 이용자 처리 방식 | 제25조 ① |
| L-7 | 동의 철회·일시 중지 요구에 응할 기술적 수단 | 제24조 ② — 현재 설계에서는 "위치 사용 끄기"(수동 출발지 전환)가 해당할 수 있는지 |
| L-8 | 위 검토 결과 PRD 확정 정책 또는 MVP 범위 변경이 필요한가 | 필요 시 PRD 개정은 사용자 결정 |
